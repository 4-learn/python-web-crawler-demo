# 13｜用 OpenCode 寫爬蟲：先寫規格再動手

> **定位**：把需求寫成一份規格交給 coding agent（OpenCode），讓它照規格寫爬蟲；並知道 AI 會在哪裡出錯。

## 學習目標

完成本節後，你應該能夠：

- 安裝 OpenCode，並用 `/init`、`/export` 完成基本操作
- 寫出一份包含「目標、來源、輸出欄位、驗收、不能做的事」的爬蟲規格
- 說出 AI 寫爬蟲常見的錯誤，並在對話中要求它修正
- 依〈上課須知〉繳交規格與 OpenCode 對話紀錄

## 情境

你是 AI 團隊的資料工程師。前兩天你親手寫了 API、靜態頁、動態頁的爬蟲，勞動基準法、職業安全衛生法都已經能抓下來。

今天主管說：

> 「問答系統還要再加好幾部法規。你不用每一支都自己從頭寫，可以讓 AI 幫你寫。但是寫出來的東西要對，壞了你要負責。」

AI 寫程式很快，但它不知道你要什麼、不知道練習站長什麼樣子、也不知道哪些事不能做。這一節要學的，是**把需求寫清楚**：先寫規格，再讓 AI 動手。

## 講解

### 1. OpenCode 是什麼、不是什麼

OpenCode 是一個在終端機裡執行的 **coding agent**（寫程式的助手）。它可以：

- 讀你資料夾裡的檔案
- 寫程式、修改程式
- 執行指令（例如 `python crawler.py`），看結果再修正

它背後接的是大型語言模型（LLM）。**本課不教 LLM 原理**：模型怎麼訓練、為什麼會這樣回答，是後面 LLM 課的內容。這裡只把 OpenCode 當作「一個很快、但需要被監督的新同事」。

```mermaid
graph LR
    A[你寫的 SPEC.md] --> B[OpenCode]
    B -->|寫程式、執行| C[crawler.py + 輸出]
    C --> D[你驗證<br/>第 14 節]
    D -->|有錯| B
```

重點在最後一步：**AI 交出來的東西，由你負責驗收**。

### 3. 基本操作

在專案資料夾裡啟動：

<!-- fn-table -->
| 函式名稱 | 說明 | 官方文件連結 |
|---|---|---|
| `opencode` | 在目前資料夾啟動 OpenCode 終端介面 | [文件](https://opencode.ai/docs/#usage) |

```bash
mkdir ~/oc-test && cd ~/oc-test
opencode
```

進入後就是 OpenCode 的**聊天視窗**：在輸入框打字、按 `Enter` 送出。畫面說明與截圖見〈[OpenCode 安裝與模型設定](https://github.com/4-learn/python-web-crawler-demo/blob/main/docs/opencode-setup.md)〉第 3 步。

常用指令：

| 指令／按鍵 | 作用 |
|---|---|
| `/init` | 讓 OpenCode 分析目前的專案，在根目錄產生 `AGENTS.md` |
| `Tab` | 切換 Plan 模式（只提計畫、不改檔案）與 Build 模式（真的動手） |
| `@檔名` | 在對話中指定某個檔案 |
| `/undo`、`/redo` | 撤銷／重做 AI 剛才做的修改 |
| `/export` | 把這段對話存成 Markdown 檔（交作業用） |
| `/connect`、`/models` | 接上模型提供者、換模型 |
| `Esc` | 中斷 AI；`Ctrl+C` 離開 OpenCode |

`AGENTS.md` 是給 AI 看的「專案說明」：專案在做什麼、怎麼執行、有哪些規矩。你可以自己編輯它，例如加一行「每次請求間隔至少 1 秒」，之後每一次對話 OpenCode 都會讀到。

:::info
`/export` 匯出的檔案會完整記錄對話。對話裡不要出現金鑰、密碼或個資，繳交前先打開看一遍。
:::

### 4. 為什麼要先寫規格

直接對 AI 說「幫我爬大量解僱勞工保護法」，它常常會這樣做：

| AI 的做法 | 為什麼錯 |
|---|---|
| 自己編一個網址 `/api/law/N0020012.json` | 沒去看網站真正的結構，網址根本不存在 |
| `for page in range(1, 3)` | 頁數寫死；法規改版多一頁就漏抓 |
| 不讀 robots.txt、不等待 | 你沒說，它就不做 |
| 直接用 Selenium | 有 API 卻開瀏覽器，慢又浪費資源 |
| 說「已完成，共 21 條」但沒有執行 | 看起來像有跑過，其實是猜的 |
| 測試沒過，就去改測試或改規格 | 讓驗收「通過」，而不是讓程式正確 |

這些錯誤的共同點：**AI 不知道的事，它會用猜的，而且猜得很有自信**。規格的作用，就是把你知道、它不知道的事寫下來。

### 5. 一份好規格的五個部分

| 部分 | 回答什麼問題 | 寫不清楚會怎樣 |
|---|---|---|
| **目標** | 要抓什麼？哪一部法規、pcode 是什麼？ | 抓錯法規、抓太多或太少 |
| **來源** | 從哪個網址？用 API 還是 HTML？什麼時候停？ | AI 自己猜網址、用錯工具 |
| **輸出欄位** | 檔名、格式、每個欄位的名稱與範例 | 欄位名稱每次不一樣，下游接不起來 |
| **驗收** | 怎樣算做對？能被檢查嗎？ | AI 說「完成了」你也無從判斷 |
| **不能做的事** | robots.txt、速率、禁用的工具、不准改規格 | AI 為了「完成任務」走捷徑 |

最常被忘記的是最後一項。人類工程師知道「不要把網站打爆」，AI 不一定知道。

### 6. 示範規格：大量解僱勞工保護法

demo 的 `SPEC.md` 以「大量解僱勞工保護法」（pcode `N0020012`，共 21 條）為例（節錄）：

<sub>📄 來源：[`13-opencode/SPEC.md`](https://github.com/4-learn/python-web-crawler-demo/blob/main/13-opencode/SPEC.md) 節錄（省略標題與說明）</sub>

```markdown
## 目標
從爬蟲練習站取得「大量解僱勞工保護法」（pcode `N0020012`）全部條文，存成 JSONL。

## 來源
- 首頁：https://4-learn.github.io/crawler-playground/
- 使用 API：`v1/api/laws/N0020012/page-1.json`，依 `next` 欄位走完分頁；`next` 是 `null` 就停。

## 輸出
檔名 `N0020012.jsonl`，一行一條，UTF-8，欄位：

| 欄位 | 說明 | 範例 |
|---|---|---|
| `pcode` | 法規代碼 | `N0020012` |
| `article_no` | 條號 | `第 1 條` |
| `chapter` | 章名，沒有就空字串 | |
| `content` | 條文全文，多段以 `\n` 分隔 | |
| `source_url` | 該條詳細頁網址 | `.../v1/laws/N0020012/articles/1.html` |

## 驗收
- 條數等於 API 的 `total`。
- 沒有重複的 `article_no`。
- 執行結束時印出條數，以及第一條和最後一條的條號。

## 限制（不能做的事）
- 先讀 robots.txt，不可請求 `Disallow` 的路徑。
- 每次請求間隔至少 1 秒；設定 User-Agent `course-crawler/1.0 (你的暱稱)`。
- 只用 `requests`，不要用 Selenium 或 Playwright。
- 不要把條數寫死在程式裡；從 API 讀取總數。
- 不要修改這份 SPEC.md。
```

逐項看它為什麼這樣寫：

- **來源寫了終止條件**（`next` 是 `null` 就停）：避免 AI 寫死頁數。
- **欄位附範例**：`第 1 條` 是「第、空格、數字、空格、條」，不寫範例 AI 可能輸出 `1` 或 `第1條`。
- **驗收可以被檢查**：「條數等於 API 的 `total`」可以用程式比對；「抓得完整」就不行。
- **印出第一條和最後一條條號**：一眼就能看出有沒有漏頭漏尾。
- **「不要把條數寫死」**：如果寫 `assert len(rows) == 21`，法規修正後程式不會發現問題。

寫規格前，自己先看一下 API 長什麼樣子。這份規格的數字是查過的：

<sub>📄 來源：在瀏覽器打開 [`v1/api/laws/N0020012/page-1.json`](https://4-learn.github.io/crawler-playground/v1/api/laws/N0020012/page-1.json) 與 `page-2.json` 看到的重點（整理後）</sub>

```text
GET v1/api/laws/N0020012/page-1.json
→ name: 大量解僱勞工保護法, total: 21, total_pages: 2, next: page-2.json
GET v1/api/laws/N0020012/page-2.json
→ next: null, 最後一條: 第 21 條
```

**規格裡的事實要自己查過**，不能也讓 AI 猜。

### 7. 交給 OpenCode

建一個自己的資料夾，把 demo 的規格複製進來：

```bash
cd ~
mkdir lay-off-crawler && cd lay-off-crawler
cp ~/python-web-crawler-demo/13-opencode/SPEC.md .
opencode
```

`~/python-web-crawler-demo` 要換成你 clone demo repo 的位置。**不要在 demo repo 裡面做**，AI 改到的檔案才不會和範例混在一起。

確認輸入框下面是老師公布的模型（不是的話用 `/models` 換），在 OpenCode 裡輸入：

```text
請閱讀 SPEC.md，照規格寫 crawler.py，完成後執行一次並把輸出筆數告訴我。
不要修改 SPEC.md。
```

比較複雜的任務，可以先按 `Tab` 切到 Plan 模式，讓它說明打算怎麼做，確認方向對了再切回 Build 模式。

AI 工作的畫面、完成時的樣子，以及實測一次花多久（約 2 分鐘），見〈[OpenCode 安裝與模型設定](https://github.com/4-learn/python-web-crawler-demo/blob/main/docs/opencode-setup.md)〉第 7 步。

### 8. 檢查 AI 的成果

AI 說「完成了」之後，**自己再跑一次**，並對照規格逐項檢查：

<!-- fn-table -->
| 函式名稱 | 說明 | 官方文件連結 |
|---|---|---|
| `wc -l 檔案` | 計算檔案行數；JSONL 一行一筆，等於筆數 | [文件](https://manpages.ubuntu.com/manpages/noble/man1/wc.1.html) |
| `head -n 1 檔案` | 只看檔案前 1 行 | [文件](https://manpages.ubuntu.com/manpages/noble/man1/head.1.html) |

```bash
python crawler.py
wc -l N0020012.jsonl
head -n 1 N0020012.jsonl
```

<!-- run-box -->
:::info
**▶ 怎麼執行**　在你自己的 `lay-off-crawler` 資料夾執行（不是 demo repo）。
:::

照規格正確執行，應該看到 21 條、第一條是「第 1 條」、最後一條是「第 21 條」，和 API 的 `total` 一致。

:::info
實測時，AI 寫出來的程式用上面三個指令檢查全部通過，**但讀程式碼才發現問題**：一次是 User-Agent 寫成 `(opencode)` 而不是 SPEC 要求的暱稱，另一次是用了第 06 節教過的陷阱 `parser.read()`。AI 每次寫的程式都不一樣，一定要自己讀一遍。
:::

再打開 `crawler.py` 看三件事：

1. 有沒有讀 robots.txt？
2. 有沒有 `time.sleep(1)` 或等效的間隔？
3. 有沒有出現 `21` 這種寫死的數字、`range(1, 3)` 這種寫死的頁數？

發現問題就在對話中要求它修正，例如：

```text
crawler.py 第 16 行 USER_AGENT 是 course-crawler/1.0 (opencode)，違反 SPEC.md「設定 User-Agent course-crawler/1.0 (你的暱稱)」。
請改成 (student)，只改這一行，改完重新執行一次。
```

好的修正要求有三個要素：**哪裡錯、違反規格哪一條、希望怎麼改**。只說「不對，再試一次」，AI 常常會改到別的地方去。

### 9. 繳交：規格與對話紀錄

延續〈上課須知〉「使用 AI 要附 prompt」的規定，本課使用 OpenCode 一律繳交：

- `SPEC.md`：你自己寫的規格
- 對話紀錄：`/export` 匯出的 `session-….md` 檔
- AI 產生的程式與輸出
- 你自己做的驗證（第 14 節會教）

老師看對話紀錄，看的不是 AI 多厲害，而是**你有沒有檢查它、有沒有要求它修正**。一次就全盤接受的對話紀錄，通常代表沒有驗收。

## Workshop

### 題目

替「職業安全衛生法」（pcode `N0060001`）寫一份 `SPEC.md`，交給 OpenCode 產生爬蟲，輸出 JSONL。

**課堂題：寫規格**（不用 AI）

1. 自己先打開 API（`v1/api/laws/N0060001/page-1.json`），查出總條數、頁數、最後一頁的 `next`，寫進規格。
2. 照第 5 段寫出**目標、來源、輸出欄位、驗收、不能做的事**五個部分。可以從 demo 的 `SPEC.md` 改起。
3. 輸出欄位至少包含 `pcode`、`law_name`、`slug`、`article_no`、`chapter`、`content`、`source_url`。
4. 驗收條件的條數要**從 API 讀取**，不能寫死。

**延伸題：交給 OpenCode**

5. 在新資料夾 `osh-crawler` 裡，把你的 `SPEC.md` 交給 OpenCode 產生 `crawler.py`。
6. 自己再跑一次、讀一遍程式，至少要求它修正一次（或說明你檢查了哪些地方、為什麼不需要修正）。
7. 建議再加 `fetched_at`、`content_hash` 欄位（第 15、16 節會用到）。
8. 用 `/export` 匯出對話紀錄。

### 預期輸出

課堂題：`SPEC.md` 五個部分都有，數字是你查過的（總共 61 條、4 頁）。

延伸題：執行 AI 寫好的爬蟲，結束訊息應類似（格式依你的規格）：

```text
共 61 條；第一條：第 1 條；最後一條：第 55 條
```

- 輸出檔 61 行，每行一個 JSON 物件
- 第 1 條內容以「為防止職業災害」開頭
- `slug` 沒有重複

繳交：課堂題交 `SPEC.md`；延伸題再加 OpenCode 對話紀錄（`/export` 匯出的檔案）、`crawler.py`、輸出的 JSONL。
